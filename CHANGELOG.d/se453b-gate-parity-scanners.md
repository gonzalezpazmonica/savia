- **SE-453 paridad OpenCode de block-force-push**: el puerto nativo (`.opencode/plugins/guards/block-force-push.ts`) dejaba pasar el force-push con opciones globales de git (`git -C dir push`) y el amend, que el hook bash bloquea, y bloqueaba `git push origin main-fix`. Usa el mismo ancla `GIT_AT`; `tests/test-gate-result-dual-binding.bats` compara bash (con y sin `jq`) y TS con las mismas entradas y corre en CI con runtime TypeScript obligatorio. Tras la revisión, ambos bindings bloquean también la orden en la segunda línea de un bloque, envuelta en `bash -c`/`sh -c`/`eval`/`then`/`{`/`xargs`, y un `--force` aunque otra parte lleve `--force-with-lease`; `--force-with-lease` a `main-fix` deja de bloquear.
- **SE-453 S3 lote 2, `security-audit-all.sh`**: un escáner que salía 1 (hallazgos) dejaba `{}` pegado tras su JSON y se contaba como 0 hallazgos (un FAIL se leía PASS). Ahora cuenta sus hallazgos, y un escáner ausente, roto o con salida ilegible es un hueco: sin hallazgos sobre el umbral sale 2 `UNKNOWN`. `result`, `verdict` y el exit siguen el mismo criterio. `--json` lleva `result` y `gaps`.
- **SE-453 S3 lote 2, `mcp-security-audit.sh`**: sin python3 cada config salía como hallazgo MCP-00; ahora sale 2 con `unknown/python3:missing_tool`. `--json` lleva `result` y `gaps`.
- **SE-453, segunda revisión de #1348 (`block-force-push`, bash y TS)**: endurecimiento del guard, no solo paridad. Ambos bindings bloquean ahora `git` con ruta (`/usr/bin/git`) o `\git`, tras envoltorios con opciones (`env -i`, `nice -n 5`, `time -p`, `timeout -s KILL 5`, elevación con `-u`, `doas`, `ionice`, `stdbuf`, `setsid`) y dentro de `bash -lc`/`bash -l -c`; el refspec `+rama` (force-push sin `--force`); `main:main`, `HEAD:main` y `refs/heads/main`; y `--force-with-lease` a `'main'` entre comillas. El puerto TS había perdido 20 de esos bloqueos respecto a `main` al anclarse. La gramática TS no tiene ambigüedades (V8 se colgaba con entradas como `git -c -a -c -a …`) y ninguna regla cruza un salto de línea. Límites conocidos: un envoltorio fuera de la lista, alias o funciones de shell no casan, y una mención de `eval`/`sh -c` seguida de una orden git dentro de un `echo` sí bloquea (falso positivo del lado seguro).
- **SE-453, `security-audit-all.sh`**: un escáner con rc 0 sin `critical`, `high` o `medium` es `unreadable`, no 0; sin python3 el hueco `python3:missing_tool` dice la causa; con `GAPS` vacío ya no aborta en bash < 4.4.
- **SE-453, tercera revisión de #1348**: `mcp-security-audit.sh` y `security-audit-all.sh` comprueban que python3 arranque, no solo que exista (un shim de pyenv sin versión daba MCP-00 por config); el agregador rechaza cuentas booleanas (`true` se colaba como entero). La paridad bash/TS cubre también el push a `"main"` entre comillas sin lease y documenta como test el falso positivo de `eval`/`sh -c` dentro de un `echo`.
- **SE-453, cuarta revisión de #1348 (`block-force-push`)**: el puerto TS sin ancla de `main` bloqueaba `su -c '…'`, `find -exec git …`, `strace`/`ssh host git …`, y el anclado de esta PR los dejaba pasar en OpenCode. Ahora `su -c`/`su - user -c`/`su -l user -c`, `-exec`/`-execdir` y `ssh <host>` son inicio de orden, y `strace`/`ltrace` envoltorios, en los dos bindings; las banderas cortas combinadas (`-fu`, `-uf`) fuerzan como `-f`. El hook bash deja `\b` (extensión GNU) por `(^|[^[:alnum:]_])`. El agregador lee como `unreadable` un `findings_count` > 0 con todas las cuentas a 0. `verdict` en `--json` admite ahora `UNKNOWN` (exit 2) además de `PASS`/`FAIL`. Límite declarado: una orden git dentro de la cadena de otro intérprete (`python3 -c "os.system('git push --force')"`) no casa en ninguno de los dos bindings, igual que antes en bash; fijado como test.
- `mcp-security-audit.sh` y `security-audit-all.sh` abortan con exit 2 si `gate_result_emit` no emite línea, en vez de producir un JSON ilegible; el test unitario TS de `find -exec` usa la barra real (`\;`); el sondeo de runtime del test de paridad importa el guard de verdad. Falso positivo conocido del hook: `PUSH_MAIN` bloquea cualquier `main`/`master` entre `push` y el siguiente separador (p. ej. un comentario `# PR a main`).
- **SE-453, quinta revisión de #1348 (`block-force-push`, bash y TS)**: la elevación con `pkexec` y `runuser`, los intérpretes `script -qc`/`script -c` y `fish`/`tcsh`/`csh -c`, y los envoltorios `unbuffer`, `watch`, `chroot <dir>` y `flock <fichero>` son inicio de orden en los dos bindings (el TS sin ancla de `main` los bloqueaba y el anclado de esta PR los dejaba pasar en OpenCode). Límite: `flock`/`chroot` con opciones que llevan argumento (`flock -w 5 f git …`) no casa. `mcp-security-audit.sh --json` sin python3 también aborta con exit 2 si `gate_result_emit` no emite línea. El test anti-ReDoS sube el umbral de 1 s a 3 s para no dar falsos rojos en un runner cargado (una regresión exponencial tarda minutos). Queda fijado como test el falso positivo de `main` como palabra dentro de un argumento del push.
- **SE-453, sexta revisión de #1348 (`block-force-push`, TS)**: la lista de envoltorios no se cierra nunca, así que el puerto TS conserva como suelo solo-OpenCode las reglas sin ancla de `main` (force, push a `origin main`/`master`, `reset --hard`): `watch '…'`, `env -S`, `flock -w 5 f`, `firejail`, `proxychains`, `unshare`, `nsenter`, `systemd-run`, `parallel` y `sg -c` vuelven a bloquear en OpenCode, ahora sin cruzar líneas y sin contar `main-fix`. Un test solo TS fija que el puerto no bloquea menos que en `main`. El test de paridad ya no fija `/usr/bin/bash` ni construye «sin jq» solo desde `/usr/bin`; queda fijado como test el falso positivo de una palabra `+x` dentro de una opción del push.
